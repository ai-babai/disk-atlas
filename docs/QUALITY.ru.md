# Единая проверка качества

```sh
scripts/setup-dev.sh   # один раз: проверка инструментов и установка pre-push hook
scripts/check.sh       # тот же запуск локально, в hook и GitHub Actions
```

Нужны Xcode **16.4 (16F6)** / Swift **6.1.2** и Python 3.9+. Без pip, Homebrew,
платных сервисов, аккаунтов и ключей. При нескольких Xcode укажи `DEVELOPER_DIR`.
Формат исправляется через `scripts/format.sh`. База сравнения — merge base с
`origin/main`, явно: `scripts/check.sh --base <commit>`.

Hook блокирует push при ошибке и требует чистый commit, чтобы проверять именно
отправляемый код. Git не включает hooks при клонировании: сначала запусти setup.
Чужой `core.hooksPath` не перезаписывается. В CI выполняется та же команда; отчёт,
LCOV и mutation logs сохраняются как artifacts. Проверку `quality` можно сделать
обязательной в branch rules. Hook сам не запускает ИИ и не переписывает код:
контрибьютор или работающий агент исправляет сбой и повторяет общий запуск.

## Планка и её область

- Строгий `swift-format`, compiler warnings как ошибки, сборка всех targets.
- Новые/изменённые функции и computed-property blocks в Sources: CC ≤10,
  структурная cognitive complexity ≤15.
- Изменённые исполняемые строки **AtlasCore**: LLVM line coverage ≥80%.
- Новые/изменённые функции **AtlasCore**: CRAP average <5, max ≤30.
- Циклы SwiftPM targets: 0; Core не импортирует GUI/CLI.
- Новые точные дубли тел функций от 9 строк отклоняются, файл Sources ≤1 000 строк.
- Generated-property тесты сортировки/перестановок/равных ключей/top-K/фильтров,
  поведенческие проверки сохранности файлов и истории.
- Четыре выбранные мутации сортировки должны компилироваться и обнаруживаться
  тестами. Ошибка сборки/окружения не считается пойманным мутантом.

При ошибке — доработка и повторный запуск. Не обходить hook через `--no-verify`,
не повышать пороги и не перегенерировать исключения ради зелёного результата.
Пороги: [policy.json](../quality/policy.json).

## Честные границы измерения

Метрики сложности считаются по SwiftSyntax, а не по словам в комментариях и
строках. Полные правила подсчёта описаны в [English contract](QUALITY.md#measurements-without-false-guarantees).
Это структурная метрика проекта, а не сертификат эквивалентности SonarQube;
семантический анализ рекурсии/графа вызовов не реализован. Есть self-checks анализатора.

Покрытие берётся из исполняемых строк LLVM LCOV. Форматирование без изменения
синтаксических токенов не создаёт фиктивного diff. Новые файлы учитываются,
отсутствие данных — ошибка, отсутствие исполняемых изменений — N/A, а не 100%.
База, числа, функции и долг доступны в `.build/quality/report.json`.

CRAP = CC² × (1 − coverage)³ + CC. Используется **line coverage как proxy**, не
basis-path coverage. Порог покрытия/CRAP не охватывает SwiftUI/AppKit и CLI:
для них остаются статические проверки, сборка и ручная проверка нативного UI.
4/4 выбранных мутанта — не полный mutation score проекта. Процессные проверки CLI
проверяют справку, обнаружение команд, страницы, ошибки, права экспорта, явное
чтение дубликатов, сигналы, конфликты установки и совместимость MCP на временных
синтетических данных. CLI собирается до запуска этих проверок.

Первичный аудит `e5f7721` выявил 29 превышений сложности. Четырнадцать обязанностей
с тех пор удалены или переработаны: части карты/инспектора, подготовка, статусы и CLI/MCP.
Осталось **15** замороженных исключений в
[legacy.json](../quality/legacy.json). Они действуют только при точном совпадении
старого тела функции. Любая правка теряет исключение. Долг явно виден в отчёте;
зелёный gate изменений не означает соответствия всей исторической кодовой базы.

## Что проверяет reviewer

- **DRY:** одно правило — одно место; совпадение смысла не всегда ловится clone check.
- **KISS:** простейшее ясное решение текущего сценария; низкая метрика сама по себе не доказательство.
- **YAGNI:** настройка/абстракция привязана к существующему требованию.
- **SOLID / SRP:** связная ответственность, ясный контракт и причина изменения;
  полезные глубокие модули вместо множества бессодержательных обёрток.
- Поведение и названия предметной области; явные побочные эффекты, маленькие
  проверяемые шаги рефакторинга, сохранность данных, отмена и ошибки; тяжёлая
  работа вне главного потока.

Это практические вопросы из инженерных принципов, а не список книг и не обещание
автоматически доказать качество архитектуры. В PR — поведение, границы, свойства
и реально выполненные проверки. Источники и определения — в [English contract](QUALITY.md).

Первая сборка скачивает закреплённую Swift Argument Parser 1.8.2 из публичного репозитория.
